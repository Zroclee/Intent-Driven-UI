## 1. 背景与现状

### 1.1 现状分析

- 通用AI应用 - 一、[基础架构设计](./通用AI应用1-架构设计.md)
- 通用AI应用 - 二、[前端AI驱动组件架构设计](./通用AI应用2-前端AI驱动组件.md)


当前我们已经完成了基础架构、后端服务架构、前端意图驱动组件架构等内容的建设。系统已具备基本的单轮对话和简单的意图识别能力。下一步，我们要深入智能体的构建，从“单体大模型调用”向“多智能体协作网络”演进，并解决随之而来的复杂上下文管理问题。

### 1.2 痛点和瓶颈
在之前的项目原型实际运行和测试中，我们发现了以下显著瓶颈：

* **大模型上下文窗口瓶颈 (Context Window Limitations)**
尽管模型支持 128k 甚至更长的窗口，但在实际工程中面临 **"Lost in the Middle"（中间迷失）** 现象。当上下文过长时，模型对位于 Context 中段的关键指令或信息的检索精度会显著下降，导致逻辑链断裂。
* **上下文腐烂 (Context Rot)**
随着对话轮数的增加，早期设定的 System Prompt（系统提示词）约束力逐渐减弱。模型开始“遗忘”最初的角色设定或业务规则，产生幻觉或偏离任务目标。
* **上下文成本和延迟 (Cost & Latency)**
全量携带历史记录会导致 Input Token 数量指数级增长，直接导致：
1. **推理成本飙升**：按 Token 计费模式下，长对话成本不可控。
2. **首字延迟 (TTFT) 增加**：Prefill（预填充）阶段耗时过长，严重影响用户体验。

我将通过以下多智能体和上下文工程来环节上述问题


## 2. 多智能体（multi agent）
这里我参考[LangChain的多智能体设计](https://docs.langchain.com/oss/python/langchain/multi-agent)

#### 2.1 为什么需要多智能体

单体 Agent（Single Agent）在处理复杂任务时已触及天花板，我们需要引入多智能体架构，理由如下：

1. **我们需要「专业分工」 (Specialization)**
一个通用的 System Prompt 很难同时兼顾“富有创意的文案撰写”和“严谨的 Python 代码审计”。通过分离关注点，我们可以让 specialized agents（如 Coder, Reviewer, Planner）各自拥有最优的 Prompt 和工具集。
2. **我们需要「自我修正」 (Self-Correction)**
单体模型往往很难发现自己的错误。多智能体架构允许引入“测试者”或“批评家”角色，构建 `Plan -> Execute -> Critic -> Refine` 的闭环，显著提高任务成功率。
3. **我们需要「复杂流程控制」 (Orchestration)**
真实业务往往是非线性的（包含条件判断、循环、并行）。多智能体架构（配合图导向的状态机）能精确控制任务流转，处理长时程任务（Long-running tasks）。

#### 2.2 多智能体模式

我们将主要探索以下三种核心模式：

* **路由模式 (Router / Handoff)**
* **描述**：由一个主控 Agent (Router) 分析用户意图，将任务分发给特定的子 Agent。
* *示例：用户问“帮我查天气”，Router 识别意图后转交给 `WeatherAgent`。*


* **监督模式 (Supervisor / Hierarchical)**
* **描述**：一个监督者 Agent 管理一组 Worker Agents。监督者负责拆解任务、分配任务、汇总结果，并决定是否需要重试。
* *示例：编写软件功能。Supervisor 指挥 Coder 写代码，Tester 运行测试，若报错则让 Coder 重写。*


* **协作网络模式 (Network / Joint Chat)**
* **描述**：Agents 之间是对等关系，基于共享状态（Graph State）互相传递消息。
* *示例：头脑风暴会议，多个角色自由发言，直到达成共识。*

#### 2.3 多智能体实践

在原型开发中我将基于多智能体的路由模式来设计架构。

1. **共享状态设计 (Shared State Schema)**
定义全局 `State` 对象，利用 WSCI 中的 **W (Write)** 策略，确保所有 Agent 对状态的修改都是原子的、可追溯的。
* `messages`: 全局消息列表。
* `next`: 下一步由谁执行。


2. **上下文隔离 (Isolation in Practice)**
利用 WSCI 中的 **I (Isolate)** 策略，Coder Agent 不需要知道 User 的闲聊历史，只需要看到 Requirement Doc 和当前的 Error Log。我们将通过 Graph 的节点定义来实现这种视野隔离。
3. **节点定义 (Node Definition)**
* **Planner Node**: 负责生成步骤。
* **Executor Node**: 负责调用工具执行。
* **Reflector Node**: 负责检查输出并提出修改意见。





## 3. 上下文工程 (context Engineering)
更多上下文的内容请参考这篇文档[上下文管理](../上下文工程/上下文工程.md)

#### 3.1 什么是上下文

在 AI 架构中，**上下文 (Context)** 不仅仅是“聊天历史记录 (Chat History)”。它是智能体做出决策所需的所有**环境状态信息**的总和。

一个完整的上下文环境包含四个维度：

1. **显式对话历史**：用户与 AI 的过往交互。
2. **用户画像与状态**：用户的偏好、权限、当前会话变量（如 `current_project_id`）。
3. **动态知识注入**：通过 RAG 检索到的相关文档片段。
4. **系统元数据**：当前时间、可用工具列表、全局配置。

#### 3.2 上下文腐烂
指上下文的信息质量随着交互进行而下降的现象，主要包括：

* **上下文缺失 (Context Missing)**
* **现象**：模型回答“我不知道”，或者因为缺乏必要的前置信息（如上一步的计算结果）而胡乱猜测。
* **原因**：关键信息被截断（Truncation）、检索失败或未能正确传递给当前 Agent。


* **上下文退化 (Context Degradation)**
* **现象**：模型“因为噪声而分心”。过多的无关信息（如闲聊、过期的错误尝试代码）占据了注意力，导致模型忽略了最新的核心指令。
* **原因**：信息信噪比低，未做有效的清洗和压缩。

#### 3.3 上下文实践
为了解决上述问题，我们采用 **WSCI (Write - Select - Compress - Isolate)** 标准化生命周期管理策略：

| 策略模块             | 核心机制                 | 实施细节                                                                                                                                                                                 |
| -------------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **W - Write (写入)** | **标准化存储与状态更新** | 所有的交互（User Input, AI Response, Tool Output）必须被标准化为统一的 `Message` 对象并持久化。不仅仅是“追加日志”，更包括更新当前的 `Global State`（如提取用户姓名、修改任务状态）。<br> |

<br>**关键点**：结构化日志、状态快照。 |
| **S - Select (选取)** | **动态检索与相关性过滤** | 并非所有历史记录都需入参。根据当前 Query 的语义，选取最相关的历史片段或知识库条目。<br>

<br>**关键点**：RAG 检索、时间滑动窗口（保留最近 N 轮）、关键事件锚点（只保留重要的 Milestone 节点）。 |
| **C - Compress (压缩)** | **信息密度优化** | 对选取的上下文进行“脱水”处理。将冗长的多轮对话合并为摘要，或将复杂的 JSON 数据简化为关键字段。<br>

<br>**关键点**：递归摘要（Recursive Summarization）、Token 剪枝、向量化表示。 |
| **I - Isolate (隔离)** | **安全边界与关注点分离** | 防止上下文污染。不同 Session 之间绝对物理隔离；同一 Session 内，System Prompt 需与 User Data 隔离（防止 Prompt Injection）；多智能体之间，各 Agent 仅能看到其任务所需的局部上下文。<br>

<br>**关键点**：会话沙箱、Prompt 结构化分隔符、Agent 视野限制。 |



## 4. 智能体原生架构
这一段参考[agent-native](https://every.to/guides/agent-native)面对智能体开发的最大的挑战就是不确定性，为了确保系统不仅是“接入了 AI”，而是真正的**智能原生 (Agent-Native)**，我们制定了以下四个维度的验收标准。

### 4.1 架构维度 (Architecture)

架构设计的核心目标是赋予 Agent 与系统深度集成的“公民权”。

* **等效性 (Parity)**：Agent 能够完成用户通过 UI 界面可以执行的所有操作。UI 不应成为 Agent 的围墙。
* **原子化颗粒度 (Granularity)**：工具（Tools）应设计为原子原语；领域工具是 Agent 的“快捷键”而非“唯一入口”。
* **可组合性 (Composability)**：通过编写新的 Prompt 即可增加新功能，而非每次都开发新的硬编码逻辑。
* **涌现能力 (Emergent Capability)**：Agent 能够完成设计阶段未明确预设的任务路径。
* **Prompt 驱动变更**：改变系统行为的手段应优先通过编辑 Prompt 实现，而非大规模重构后端代码。

### 4.2 实现维度 (Implementation)

实现层决定了 Agent 运行的透明度、确定性与响应速度。

| 准则项                      | 验收要求                                                                                  |
| --------------------------- | ----------------------------------------------------------------------------------------- |
| **资源声明 (Capabilities)** | 系统提示词（System Prompt）必须明确包含当前 Agent 可调用的所有资源、工具和权限边界。      |
| **共享数据空间**            | Agent 与用户在同一个数据空间（Data Space）内协作，Agent 的操作对用户透明可见。            |
| **实时 UI 反馈**            | Agent 执行的动作必须立即在 UI 上得到体现（例如自动填充表单、更新状态球），无感知延迟。    |
| **全量 CRUD 能力**          | 每一个业务实体（Entity）都必须对 Agent 开放完整的增删改查权限，保证操作闭环。             |
| **动态能力发现**            | 外部 API 接入时，尽可能采用动态能力发现（Dynamic Discovery）机制，而非静态硬编码。        |
| **显式完结信号**            | Agent 必须有明确的“任务完成”信号（Signal Completion），严禁使用启发式猜测来判定任务结束。 |

### 4.3 产品维度 (Product)

从用户体验和迭代逻辑衡量系统的进化能力。

* **零学习成本**：简单的请求应立即生效，用户无需学习复杂的 Prompt 工程技巧。
* **支持极客探索**：允许高级用户（Power Users）通过特定的指令将系统推向非预设的复杂场景。
* **观察驱动演进**：通过观察用户对 Agent 的自然语言请求，发现真实需求痛点，从而驱动产品迭代。
* **分级审批机制**：根据任务的风险等级和可逆性（Reversibility），自动匹配相应的审批流（例如：发送邮件需确认，查询报表无需确认）。

### 4.4 移动端适配 (Mobile)

针对移动端环境的特殊不稳定性进行的容错设计。

* **断点续传 (Checkpoint/Resume)**：系统必须能够处理移动端应用切换、中断后的上下文恢复，确保长任务不因进程挂起而丢失。
* **云端优先存储**：采用 iCloud 或同类同步机制，本地存储作为兜底，确保跨设备上下文一致性。
* **后台执行优化**：合理利用后台运行时间，确保 Agent 的耗时计算或 API 调用在不影响前台性能的情况下完成。
